# 训练与验证指南（二分类 · 36×36 输入）

面向"只有一批实拍数据"的使用者，回答四个问题：**数据集怎么指定、用什么格式输入、怎么训练、结果怎么验证 / 可行性怎么判断。**

> 当前任务：给定 36×36 灰度 ROI（目标居中、外圈为背景），二分类判定**是否为无人机/飞机**。模型为 `DroneNet`（~7.6 万参数），损失 `BinaryFocalLoss`。

---

## 0. 先划分数据集（按帧分组，防泄漏）

如果你手上只有一整批原始样本（如 `data/base_data/{drone,non_drone}/*.png`），**先划再训**：

```bash
python scripts/split_data.py --src data/base_data --dst data --dry-run   # 先看计划
python scripts/split_data.py --src data/base_data --dst data             # 落盘
```

**为什么必须按帧分组**：实拍文件名形如 `ff90_1013_021_000525_001049.png`
（序列 ID + **帧号** + 裁剪序号）。同一帧号下有多个相邻裁剪块，内容高度相似；
若逐文件随机划分，同一帧的块会同时进入 train 和 val，**指标会严重虚高**。
脚本默认 `--group-by frame`，保证同一帧（含其正负样本）只落在一个集合。

| 参数 | 默认 | 说明 |
|---|---|---|
| `--train / --val / --test` | 0.7 / 0.15 / 0.15 | 三者之和须为 1；**只想要 train/val 就传 `--test 0`** |
| `--group-by` | `frame` | `frame`=同帧同组（推荐）；`clip`=整段视频同组；`file`=逐文件（不推荐） |
| `--block` | 1 | 每 N 个连续帧号合并为一组（≥2 可进一步压低相邻帧的时序泄漏） |
| `--mode` | `copy` | `copy` / `symlink`（省空间）/ `move` |
| `--seed` | 42 | 划分随机种子 |
| `--clean` | 关闭 | 写入前清空目标目录已有文件（重划时用） |

脚本会打印各类各集合的数量与占比，并做**泄漏自检**（同一分组不得跨 split）。
划分后建议再手工复核一次：

```bash
for s in train val test; do find data/$s -type f -printf "%f\n" | \
  awk -F'_' -v S=$s '{print $1"_"$2"_"$3"_"$4"\t"S}'; done | sort -u | \
  awk -F'\t' '{c[$1]=c[$1]" "$2} END{bad=0; for(f in c){n=split(c[f],a," ");
  if(n>1){print "泄漏:",f,c[f]; bad++}} if(!bad) print "PASS: 无同帧跨集"}'
```

> 组数少、组内样本量大时，各集合比例只能逼近目标（实测 350 张 / 32 组：
> drone 69.6/15.2/15.2%，non_drone 66.2/15.6/18.2%），偏差 ±3pp 属正常；
> 这是**防泄漏必须付的代价**，不要用逐文件随机划分去"凑比例"。

## 1. 数据集如何指定？

通过命令行参数二选一：

| 场景 | 参数 | 说明 |
|---|---|---|
| **没有实拍数据**（先跑通管线/预训练） | 不传 `--data-root` | 程序用**在线合成**数据，无限量、无需准备文件 |
| **有实拍数据**（微调/正式训练） | `--data-root <根目录>` | 程序读取 `<根目录>/train` 和 `<根目录>/val` |

```bash
# 合成数据（无需任何文件）
python scripts/train.py --epochs 30 --n-per-class 5000 --device cuda

# 实拍数据（指向你的数据根目录）
python scripts/train.py --data-root data --epochs 15 --device cuda
```

## 2. 数据集格式（输入规范）

### 目录结构（二分类，负样本无需细分）
```
data/
├── train/
│   ├── drone/*.png        # 正样本：飞机/无人机 ROI
│   └── non_drone/*.png    # 负样本：天空/云边缘、杂波等，混入即可
└── val/
    ├── drone/*.png
    └── non_drone/*.png
```

- **标签由"子文件夹名"决定**，不需要任何 CSV/标注文件。
- **正类文件夹名**（不区分大小写，命中即为正样本）：`drone / plane / target / uav / positive`；**其余任何文件夹名都算作负样本**。
- 也兼容旧的四类布局 `drone / sky_edge / cloud_edge / background`——此时仅 `drone` 为正，其余三类自动并入负类。

### 单张图片要求
| 项目 | 要求 |
|---|---|
| 格式 | `.png / .jpg / .jpeg / .bmp` |
| 通道 | 任意，读取时自动转灰度（取亮度 Y） |
| 尺寸 | **任意，且绝不会放大**（方案 B）：>36 **等比缩小**（最长边缩到 36，`INTER_AREA`）后居中填充到 36×36；<36 居中放入 36×36 画布。填充区填 0 并用掩码通道标记 |
| 构图 | **目标大致居中**（外圈背景用于局部亮度基准，能留则留） |

> **为什么不再 resize**（2026-10-22 改动）：实拍数据实测 3412 张中仅 4.2% 是 36×36，
> 边长从 12 到 36 不等。原先统一 resize 会把 16×16 的 ROI **放大 2.25 倍**，
> 目标在画面中的相对尺寸被撑大，与合成数据（36 画布内的 2~18px 小目标）尺度语义错位。
> 现在保持目标的**绝对像素尺寸**，靠掩码通道告诉网络哪些区域是填充。
> 合成管线同步模拟该分布（`crop_prob=0.6`, 有效区 `[12, 36]`），否则训练/推理仍不一致。

### 两个必须遵守的点
1. **负样本要含"硬负例"**：天空边缘、云层边缘、远处景物暗斑等——否则模型只会区分"飞机 vs 纯天空"，遇到边缘干扰会误报。
2. **按视频场次/场景划分 train/val**，同一场景的帧不得跨集合，否则验证指标虚高。

## 3. 如何训练？

## 推荐配方（2026-10-22 起）：**纯实拍训练，不使用合成数据**

```bash
python scripts/train.py --data-root data \
    --epochs 80 --batch-size 32 --lr 3e-4 \
    --monitor f1 --patience 15 --pos-weight auto \
    --no-handcrafted --out runs/dronenet.pt
```

| 参数 | 取值理由（实拍实测） |
|---|---|
| `--pos-weight auto` | train 集正负比 1:3.02（337/1019），自动 `pos_weight=3.024`。实测 test 集 **FAR 从 0.0094 降到 0.0047**、F1 0.9863→0.9931 |
| `--no-handcrafted` | 实拍上纯 CNN 与带手工特征**等价**（test F1 均 0.993）；纯 CNN 无 OpenCV 依赖、预处理快 28×、可整网上 NPU |
| `--monitor f1` | 直接按业务指标选工作点；早停实测落在第 25 轮 |
| `--batch-size 32` | 1356 张训练集 → 每轮 42 步；用默认 256 则每轮仅 6 步 |

**当前实测结果（纯实拍，test 集 285 张）**：

| 阈值 | P | R | F1 | FAR/ROI |
|---|---|---|---|---|
| 0.3 | 0.947 | 1.000 | 0.973 | 0.0188 |
| **0.5** | 0.986 | **1.000** | **0.993** | 0.0047 |
| 0.8 | **1.000** | 0.917 | 0.957 | **0.0000** |

AUC 0.9998（bootstrap 95% CI [0.999, 1.000]）。推荐部署阈值 **0.5**（F1 最优）；
若要求零误报则取 **0.8**（召回降至 0.917）。

> 合成数据当前只用于**管线自检**（`scripts/validate_model.py` 用合成样本做冒烟），
> 不再参与训练。若日后实拍样本不足（<200 张）再考虑启用。

### 强烈推荐：纯 CNN（`--no-handcrafted`）

消融实验（合成数据，10 epochs × 4800 样本，相同种子）表明**去掉手工特征分支反而更好**：

| 版本 | AUC | AP | F1 | recall@FAR=1e-3 |
|---|---|---|---|---|
| 保留 8 维手工特征 | 0.9281 | 0.8923 | 0.7720 | 0.5967 |
| **纯 CNN** | **0.9452** | **0.9190** | **0.8210** | **0.6467** |

**为什么**：手工特征是**归纳先验**——小数据、少训练步时帮模型快速收敛；但它是人工设计的**有损压缩**（把整个连通域压成一个"紧凑度"标量、把梯度分布压成一个"对称度"标量）。训练充分后，CNN 自己学到的高维表示信息量更大，反而更强。**数据充足 → 用纯 CNN。**

> ⚠️ 别被欠训练误导：3 epochs 的那次实验曾得出"手工特征更优"（0.647 vs 0.426），那是**收敛速度**的差异，不是最终上限。做消融务必训练充分（≥10 epochs / 数千步）。

**附加收益（部署侧，桌面 CPU 实测，统一按每 ROI 折算）**：

| 版本 | 预处理 | 推理 | 端到端（batch=30 批总 → 每 ROI） |
|---|---|---|---|
| 带手工特征 | 0.124 ~ 0.139 ms/ROI | 2.81 ms/批 | 7.55 ms/批 → **0.252 ms/ROI** |
| **纯 CNN** | **0.005 ms/ROI（快约 28×）** | 4.29 ms/批 | → 约 **0.15 ms/ROI** |

整网变成 tensor→tensor、无 OpenCV 依赖，可整块上 NPU（RKNN 等）。

> ⚠️ 口径提醒（2026-10-21 修正）：`benchmark_onnx.py` 打印的 B/C 段是**批总耗时**（batch=30），
> 必须除以批大小才能与"每 ROI 时延预算"比较，否则会误判不达标。脚本已自动折算并给出结论。

### 常用参数
| 参数 | 默认 | 说明 |
|---|---|---|
| `--data-root` | 空 | 实拍数据根目录；空=在线合成 |
| `--init-from` | 空 | **预训练权重路径，用于微调**；空=随机初始化 |
| `--n-per-class` | 3000 | 合成数据每类样本数（仅合成模式） |
| `--epochs` | 10 | 训练轮数（微调建议 10~20，小学习率） |
| `--batch-size` | 256 | 批大小；**实拍小数据集（几百张）务必改小到 16~32**，否则每 epoch 只有 1 次参数更新 |
| `--lr` | 3e-4 | 学习率；**微调建议降到 1e-4 ~ 5e-5** |
| `--no-handcrafted` | 关 | **推荐开启**：去掉手工特征分支，用纯 CNN（见上节消融结论）；开关须与预训练一致 |
| `--device` | 自动 | `cuda` 或 `cpu` |
| `--out` | runs/dronenet.pt | 最优模型保存路径 |
| `--patience` | 8 | **早停**：连续 N 轮监控指标无改善即停止；**0=关闭早停跑满轮数** |
| `--min-delta` | 1e-4 | 早停：视为"有改善"的最小变化量 |
| `--monitor` | val_loss | 早停/择优监控指标：`val_loss`（越小越好）或 `f1` / `auc`（越大越好） |

> 微调时注意：**`--no-handcrafted` 的设置要和预训练时一致**，否则权重不完全匹配（程序会打印 missing/unexpected 数量提示）。

### 早停机制（防止过拟合与无效训练）

训练默认开启早停（`--patience 8`，监控 `val_loss`）：连续 N 轮监控指标没有超过 `--min-delta` 的改善就停止，
并**自动恢复最优轮次的权重**（不会停在过拟合的最后一轮）。日志形如：

```
[epoch 11] train_loss=... val_loss=... val_loss=0.0612 (1.2s)
[早停] val_loss 连续 3 轮无改善 (阈值 min_delta=0.0001), 在第 11 轮停止训练
最优模型已保存到 runs/... [监控 val_loss] (早停于第 11 轮)
```

**怎么选监控指标**：

| 监控项 | 适用场景 |
|---|---|
| `val_loss`（默认） | 通用；关注整体概率校准 |
| **`f1`** | **推荐**：业务最关心"查准又查全"时 |
| `auc` | 数据正负比悬殊、阈值尚未确定时 |

> 合成数据实测：同样 40 轮预算，监控 `f1`（patience=4）在第 ~15 轮停止，
> FAR/ROI 为 **0.0033**；监控 `val_loss`（patience=3）在第 11 轮停止，FAR/ROI 为 0.0100
> —— 直接按业务指标早停能得到更低虚警的工作点。

**常用组合**：
```bash
python scripts/train.py --data-root data --epochs 60 --monitor f1 --patience 10 --lr 1e-4
python scripts/train.py --epochs 30 --patience 0        # 关闭早停, 跑满轮数做消融对照
```

> ⚠️ 做消融对比时务必**固定 epochs 或同时关闭早停**，否则不同分支停在不同轮次，结论不可比。

### ⚠️ 小数据集必须调小 batch_size（2026-10-21 修复）

默认 `--batch-size 256` 面向合成大数据。实拍样本只有几百张时，若 `batch_size >= 样本数`，
DataLoader 会变成 **0 个 batch**，导致 `train_loss` 计算除零崩溃，并连带触发
`lr_scheduler.step() before optimizer.step()` 告警。

脚本现已自动保护（`drop_last` 自适应 + 空 DataLoader 报错 + 打印建议），但**仍建议主动调小**：

| 配置 | 每 epoch 更新步数 | 实测（236 张训练集，15~30 epochs） |
|---|---|---|
| `--batch-size 256`（默认） | 1 步 | F1 0.52、**FAR 1.0**（几乎没学到） |
| **`--batch-size 32`** | 8 步 | **F1 0.973、FAR 0.0** |

```bash
python scripts/train.py --data-root data --epochs 30 --batch-size 32 --lr 3e-4 \
    --monitor f1 --patience 10
```

> **正样本极少时**：`BinaryFocalLoss` 已支持 `pos_weight`，但当前脚本未自动启用。
> 若实拍正负比悬殊（如 1:50），建议在 `scripts/train.py` 中按 `pos_weight = n_neg / n_pos` 传入，
> 否则模型会偏向预测负类、召回偏低。

## 4. 结果如何验证？

训练结束后会打印一份二分类报告，读懂它即可：

```
=== 二分类: 是否无人机 ===
  precision / recall / f1 / far_per_roi        # 在阈值 0.5 下的指标
=== 无人机检测 (AUC / AP / 固定 FAR 下召回率) ===
  auc / ap / recall@far0.01 / recall@far0.001 / recall@far1e-05
```

| 指标 | 含义 | 怎么看 |
|---|---|---|
| `precision` | 判为无人机的里有多少是真的 | 高=误报少 |
| `recall` | 真无人机里抓回来多少 | 高=漏检少（业务更看重） |
| `far_per_roi` | 每个 ROI 的虚警率 | 越低越好 |
| `auc` | 阈值无关的整体区分能力 | 越接近 1 越好 |
| `recall@far1e-4` | **虚警率压到 1e-4 时的召回率** | 最贴近业务的指标 |

**选工作点（部署阈值）**：按业务允许的虚警率选。例如要求 FAR≤1e-4，就看 `recall@far1e-4` 对应的分数阈值作为部署阈值；`recall@far*` 越高说明在低虚警下仍能保住召回。

## 5. 如何验证模型可行性？（验收清单）

按这个顺序走，能较快判断"这条路行不行"：

1. **规则基线对照**（证明学习法确实强于传统法）
   ```bash
   python scripts/baseline_eval.py --n-per-class 500
   ```
   把它的 F1/AUC 与 CNN 对比，CNN 应显著更高。若 CNN 没明显优势，说明管线/数据有问题。

   合成集参考值（2026-10-21，1500 样本/类 × 15 epochs）：

   | 方法 | F1 | AUC | FAR/ROI |
   |---|---|---|---|
   | 规则基线 | 0.019 | 0.708 | 0.020 |
   | **DroneNet** | **0.876** | **0.958** | **0.0089** |

   规则基线的特征是"**高虚警 + 低精确率**"（精确率仅 ~0.14）：它把大量云/天空边缘的暗区也报成目标，
   这正是"传统算法无法区分"的量化表现。

2. **合成冒烟**：合成预训练后，`recall@far1e-3` 应明显可用（合成数据只验证管线，不代表实拍水平）。

3. **实拍验证（关键）**：微调后，**必须看 100% 实拍的验证集指标**，别看合成集。
   - 可行性参考线（初始目标）：实拍 AUC ≥ 0.9、`recall@far1e-3` 达到业务可接受水平。
   - 数据少时用 **K 折交叉验证**（K=5，按场景分组）报均值±标准差，别信单次划分。

   **评估 test 集（训练脚本只吃 train/val，test 必须单独评估）**：

   ```bash
   python scripts/evaluate.py --ckpt runs/finetune.pt --data-root data --split test
   python scripts/evaluate.py --ckpt runs/finetune.pt --data-root data --split test --sweep
   ```

   `--sweep` 打印阈值扫描表（各阈值下 P/R/F1/FAR），用于挑部署工作点；
   默认还会列出前 10 个误报/漏检文件名，便于失败归因。

   > ### ⚠️ 单场景数据的指标会严重虚高（2026-10-21 实测）
   > 首批 350 张样本中 **344 张来自同一段视频 `ff90_1013_021`**。虽然已按帧分组划分
   > （无同帧跨集），但 train/val/test 仍是**同一场景、同一背景、同一光照**，
   > 模型可以记住该场景的背景统计（云的形状、地面轮廓位置）而非目标本身。
   > 实测微调后 test 集 P/R/F1 全为 1.000、AUC 1.000 —— **这不代表真实泛化能力**。
   >
   > 应对：
   > 1. **补多段视频**：不同场地 / 时段 / 天气 / 机型，每段视为一个分组；
   > 2. **留一整段交叉验证**（leave-one-clip-out）：用 `--group-by clip` 划分，
   >    每次留一整段做验证，轮换后报均值±标准差，这才是可信的泛化指标；
   > 3. 在**未见场景**的测试集上复测后才可下结论。

### 3.1 留一段视频交叉验证（跨场景泛化的判决性实验）

同场景划分的指标再好也不能说明泛化能力。用 `scripts/cross_validate.py` 做
**leave-one-clip-out**：每次留一整段视频做验证，其余全部训练，轮换后看各段差异。

```bash
python scripts/cross_validate.py                     # 默认 30 epochs, batch 32
python scripts/cross_validate.py --epochs 50 --batch-size 16 --lr 1e-4
```

**2026-10-21 实测（3 段视频，其中 021 有 344 张、036 有 154 张）**：

| 训练段 | 验证段 | F1 | FAR/ROI | AUC |
|---|---|---|---|---|
| 021（350 张） | 036（154） | 1.000 | 0.000 | 1.000 |
| 036（160 张） | 021（344） | **0.534** | **0.995** | 0.927 |
| **平均** | | **0.767** | | 0.963 |

> 结论：**跨场景泛化尚未成立**。两个方向严重不对称——用"样本多、负样本更难"的 021 训练时能覆盖
> 036 的分布（F1=1.0），反过来则几乎全误报（FAR≈1.0）。这说明当前模型很大程度在**记忆场景**，
> 而非学到目标本质。
>
> 应对：① 补不同场地/时段/天气/机型的视频（每段 ≥100 张）；② 把失败方向的误报样本
> （`scripts/evaluate.py --show-errors` 会列出文件名）回填为**难负样本**；③ 反复跑本脚本，
> 直到各段指标接近且均值达标。

### 3.2 FAR 有"可分辨下限"，别被 recall@far1e-4 误导

FAR 的最小可分辨粒度是 **1/负样本数**。负样本只有几十个时，`recall@far1e-4`
实际上退化成"一个误报都不许有时的召回"，换个划分集就能从 0.19 跳到 1.0。

| 想测的 FAR | 至少需要的负样本数 |
|---|---|
| 1e-2 | ≥ 1,000 |
| 1e-3 | ≥ 10,000 |
| 1e-4 | ≥ 100,000 |

代码已加保护：`drone_pr()` 返回 `min_resolvable_far`，报告里对低于下限的 FAR 目标
自动打印 ⚠️ 告警；`scripts/evaluate.py` 额外给出 **bootstrap 95% 置信区间**
（默认 300 次重采样，`--boot 0` 关闭），区间过宽时会提示样本量不足。

4. **消融实验**（验证设计有效性）：
   ```bash
   python scripts/train.py --data-root data --no-handcrafted ...   # 去手工特征
   ```
   对比保留/去掉手工特征的差异，判断该分支是否真正有帮助。

5. **失败案例分析**：把验证集里的误报/漏检样本（Top-N）挑出来人工看，归因（过曝？目标太小？边缘恰好闭合？），回头调合成管线参数域或补数据。

6. **消融复跑（开关决策）**：在**实拍数据**上用相同脚本对比“纯 CNN”与“CNN+手工特征”，确认纯 CNN 在真实分布上仍然占优（合成数据上已验证纯 CNN 更优，见第 3 节）。做消融务必**训练充分**（≥10 epochs），否则会得到误导性结论。

7. **鲁棒性测试**：对验证集注入额外噪声/模糊/亮度漂移，看性能-退化曲线是否平缓。

## 6. 模型正确性验证与 ONNX 导出

### 6.1 训练产物冒烟检查（理论运行验证）
```bash
python scripts/validate_model.py --ckpt runs/finetune.pt
```
不依赖真实部署，用合成数据检查四件事：**权重能否严格加载**（架构一致，strict）、**输出是否为合法概率**（形状 (N,)、取值 [0,1]、无 NaN/Inf）、**正样本均分是否高于负样本**、**合成集 AUC 是否 > 0.5**。全部 PASS 退出码 0，任一 FAIL 退出码 1（可接入 CI）。

### 6.2 ONNX 导出
```bash
python scripts/export_onnx.py --ckpt runs/finetune.pt --out runs/dronenet.onnx
```
- 输入签名**按训练时的开关自动决定**：
  - 默认（带手工特征）：`roi (batch,2,36,36)` + `feat (batch,8)`；
  - **纯 CNN（`--no-handcrafted`）：只有 `roi (batch,2,36,36)`** —— 无需在部署侧算 8 维手工特征，最适合整网放 NPU；
- 输出统一为 `prob (batch,)`（已含 sigmoid，直接是无人机概率）；
- 批大小动态可变，opset 17；导出后自动做 onnx 结构校验；
- 注：torch≥2.9 导出器会把权重写成伴生 `*.onnx.data`，本脚本已自动合并为**单个自包含 .onnx**，部署不会漏文件。

### 6.4 性能基准（判断是否满足部署时延预算）
```bash
python scripts/benchmark_onnx.py --onnx runs/dronenet.onnx --sizes 1,30,256 --budget-ms 2
```
分三段测：预处理（encode_roi 或纯 resize）、模型推理、端到端，并直接对照你给的时延预算。
**在有 NPU 的开发板（如 RK3588）上运行它，即可判断 CPU 方案是否够用。**

桌面 CPU 实测参考（batch=30，括号内为折算到每 ROI）：

| 版本 | 预处理 | 推理（批总） | 端到端（批总 → 每 ROI） |
|---|---|---|---|
| 带手工特征 | 0.124 ms/ROI | 2.81 ms | 7.55 ms → **0.252 ms/ROI** |
| **纯 CNN** | **0.005 ms/ROI** | 4.29 ms | → 约 **0.15 ms/ROI** |

> 预算参数 `--budget-ms 2` 是**每 ROI**口径，脚本会先折算再判定达标与否。

### 6.3 ONNX 一致性验证（关键步骤）
```bash
python scripts/verify_onnx.py --ckpt runs/finetune.pt --onnx runs/dronenet.onnx --tol 1e-4
```
验证流程三步：
1. **输入数据准备**：合成真实分布样本（覆盖 4 类语义）+ 随机输入（极端值域，边界覆盖），同一批输入分别喂给两个模型；
2. **推理结果对比**：PyTorch 与 ONNX Runtime **统一在 CPU** 上推理（消除设备差异），逐样本比较概率输出，并比对 0.5 阈值下**分类决策是否完全一致**；
3. **误差容忍范围**：统计 `max_abs_diff` / `mean_abs_diff`，默认 `tol=1e-4`（float32 数值精度损失量级）；超差或决策不一致即 FAIL，并打印最差样本的两侧输出便于定位。

## 附：当前合成数据口径（供对照实拍采集）
- 目标像素尺度：2×2 ~ 18×18（含极小目标），size-aware 模糊保证极小目标可学；
